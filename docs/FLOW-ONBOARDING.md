# 기업 신청 → 로그인 → 온보딩 · BE 인계 문서

> **목적:** 프론트가 이미 만들어 둔 화면이 **어느 시점에 무엇을 보내고 무엇을 돌려받아야 하는지**를 BE가 알 수 있게 적는다.
> **주의:** 아래 엔드포인트·필드는 **프론트가 필요로 하는 값**이다. 경로·메서드·이름은 BE가 정하면 되고, 정해지면 프론트는 매퍼만 고친다(`features/*/server.ts`·`actions.ts`).
> **현재 상태:** 이 흐름 전체가 **목(mock)** 으로 돌아간다. 실제로 호출하는 API는 **하나도 없다.**
>
> **읽는 순서:** 개발하면서 옆에 띄워둘 거면 **[부록 A](#부록-a-엔드포인트-요약-구현용)** 부터 본다(엔드포인트 표 + 복붙용 JSON). 본문은 "왜 이렇게 되는가"를 설명한다.

---

## 0. 한눈에

```
[1] 기업 등록 신청        (비로그인)  POST 신청서
      ↓  BE·운영자 검토 → 승인
[2] 승인 메일             (BE 발송)   기업 코드 + 대표 계정(ID/첫 비밀번호)
      ↓
[3] 로그인                 2단계: ① 기업 코드로 회사 확인 → ② 이메일·비밀번호
      ↓  httpOnly 쿠키 발급(companyId·role·isAdmin 포함)
[4] 온보딩 1~3단계        대표(OWNER)만. 부서 → 직급 → 사원 초대
      ↓  [완료]에서 한 번에 커밋
[5] 온보딩 4단계 · 결제    /onboarding/payment — **결제해야 넘어간다**
      ↓
[6] 워크스페이스           /owner
```

핵심 성질 4가지 — 이게 곧 BE 요구사항이다.

1. **기업 코드는 회사가 짓는 게 아니라 승인 시 BE가 발급**한다. (`NOVA-7K3D` 같은 모양)
2. **한 계정 = 한 기업.** 워크스페이스 전환 없음. 기업 식별은 **세션(쿠키)** 이고 **URL·쿼리에 절대 넣지 않는다.**
3. **온보딩은 [완료]에서 한 번에 커밋**한다. 1~3단계는 브라우저가 임시 보관(`sessionStorage`)한다.
4. **사원 초대 = 계정 발급.** 링크 가입이 아니다. 보내는 순간 계정이 생긴다.
   ⚠️ **좌석을 소모하지 않는다**(2026-08-04) — 인원은 과금 단위가 아니다.
5. **무료 요금제도 체험 기간도 없다**(2026-08-04). 온보딩 마지막 단계에서 **결제를 마쳐야** 워크스페이스가 열린다.

## 1. 기업 등록 신청 (`/register`)

비로그인 화면. 대표가 회사를 등록해 달라고 신청하는 단계다.

### 프론트가 보내는 값

| 필드             | 타입   | 검증(프론트가 이미 거는 규칙)                     | 비고                         |
| ---------------- | ------ | ------------------------------------------------- | ---------------------------- |
| `companyName`    | string | 공백 제거 후 1자 이상                             | 기업명                       |
| `businessNumber` | string | `^\d{3}-\d{2}-\d{5}$` (하이픈 포함 10자리)        | **모양만** 본다              |
| `place.address`  | string | 1자 이상                                          | 카카오 지도에서 고른 주소    |
| `place.lat/lng`  | number | 숫자면 통과 (**지도 못 쓰면 `0`으로 올 수 있다**) | 좌표 없이 주소만 올 수 있다  |
| `managerName`    | string | 1자 이상                                          | 담당자(=대표 계정이 될 사람) |
| `email`          | string | `@` 포함                                          | **승인 메일이 가는 주소**    |
| `phone`          | string | `^[\d-]{9,15}$` **그리고** 숫자만 9자 이상        | 필수                         |

> ⚠️ 프론트 검증은 **편의**다. 같은 규칙을 BE가 다시 걸어야 한다. 특히 `lat/lng = 0`은 정상 입력으로 취급하고, 필요하면 BE가 주소로 다시 지오코딩한다.

### BE가 해야 하는 일

1. 신청서 저장 (상태: `대기`)
2. **사업자등록번호 상태조회**(국세청) — 폐업·휴업이면 반려. 프론트는 모양만 봤고 실존 여부는 모른다.
3. 운영자 검토 → 승인/반려
4. 승인 시 **기업 코드 발급** + **대표(OWNER) 계정 생성** + 담당자 메일로 발송

> ⚠️ **사업자등록번호로는 신청자가 진짜 대표인지 못 가린다.** 그 값은 사실상 공개 정보라 아는 사람이면 누구나 통과한다. **실질적인 관문은 승인 단계의 사람**이다 — 자동 승인으로 열면 아무나 남의 회사 이름으로 워크스페이스를 만든다.

### 필요한 엔드포인트

```
POST /companies/registrations
  req  : 위 표 그대로
  res  : 201 { registrationId }        // 프론트는 지금 아무것도 안 쓴다. 접수만 되면 된다.
  err  : 400 필드별 오류 { errors: { businessNumber: "...", ... } }
         409 이미 신청/등록된 사업자등록번호
```

응답 오류는 **필드 이름을 키로** 주면 그대로 인라인 표시된다. 통짜 메시지면 폼 위에 한 줄로만 뜬다.

### 신청 직후 화면 (`/register/done`)

"접수됐어요 · 영업일 1~2일 안에 결과 메일" 안내만 띄운다. 로그인 버튼을 주 버튼으로 두지 않는다 — **아직 코드가 없어 눌러도 막히기 때문**이다.

> ⚠️ 현재 BE가 신청 즉시 계정 메일을 보내고 있다면, 이 화면의 "검토 후 승인" 문구와 어긋난다. **승인 흐름을 넣을지**를 확정해 달라 — 문구는 승인 흐름 기준으로 써 뒀다.

## 2. 승인 메일 (BE 발송)

**메일 하나에 세 가지가 들어가야 한다.**

- 기업 코드 (`NOVA-7K3D` — 로그인 1단계에 넣는 값)
- 대표 계정 이메일 (= 신청서의 `email`)
- 첫 비밀번호

> ⚠️ 코드 모양은 **발급받은 값처럼** 보여야 한다. `ACME-2026`처럼 회사명+연도로 만들면 사용자가 직접 지어내는 값으로 오해하고 아무 값이나 넣는다.

## 3. 로그인 (`/login`) — **2단계다**

카카오워크 문법. 한 화면에서 단계만 바뀐다.

### 1단계 · 기업 코드로 회사 확인

```
GET /companies/by-code?code=NOVA-7K3D      (또는 POST /companies/lookup)
  res  : 200 { code, name }                 // name을 화면에 보여준다("노바랩스에 연결됐어요")
  err  : 404 코드 없음
```

- 대소문자·앞뒤 공백은 **프론트가 정규화**해서 보낸다(메일에서 복사하면 공백이 붙는다). BE도 같이 정규화하면 안전하다.
- 확인에 성공하면 프론트가 `{code, name}`을 **`localStorage`에 기억**한다 → 다음 방문 때 1단계를 건너뛴다.
- ⚠️ **기업 코드는 자격증명이 아니다.** 회사를 가리키는 식별자일 뿐이라 저장해도 된다. 이 응답만으로는 아무 권한도 생기지 않는다.

### 2단계 · 이메일 + 비밀번호

```
POST /auth/login
  req  : { companyCode, email, password, keepSignedIn }
  res  : 200 + Set-Cookie(httpOnly)  또는  토큰 (BFF가 쿠키로 굽는다)
  err  : 401 자격증명 불일치
         403 승인 대기/정지된 기업
```

**토큰(또는 세션)에 반드시 들어가야 하는 값:**

| 값                                   | 왜 필요한가                                                                                                                      |
| ------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------- |
| `companyId`                          | 멀티테넌시 격리. **URL에 안 넣으므로 여기 없으면 회사를 구분 못 한다.**                                                          |
| `userId`                             | 리소스 소유권 판정(회의 담당자 등)                                                                                               |
| `role`                               | `OWNER` / `LEADER` / `MEMBER`                                                                                                    |
| `isAdmin`                            | **겸직 여부. `role` 하나로는 알 수 없다** — 없으면 겸직자가 운영 기능을 못 쓴다                                                  |
| `departmentPath` 또는 `departmentId` | LEADER가 자기 부서 전체를 관리한다 — 부서 경로가 없으면 범위 판정 불가                                                           |
| `isOnboarded`                        | 온보딩 1~3단계를 마쳤는지                                                                                                        |
| `subscriptionStatus`                 | `ACTIVE` / `CANCELING` / `UNPAID` / `EXPIRED`. **결제 전이면 `/onboarding/payment`에서 막고, 만료면 워크스페이스에 못 들어온다** |

- 비밀번호 **규칙(길이·문자 종류)은 프론트가 모른다.** 지금은 "비었는지"만 본다 — BE 정책을 알려주면 화면에도 반영한다. 임의로 정하면 서버가 받아줄 비밀번호를 화면이 막는다.
- `keepSignedIn`(로그인 상태 유지) 체크값이 **쿠키 수명(`maxAge`)** 이 된다.
- 프론트는 브라우저에 **토큰을 저장하지 않는다.** 브라우저 → Next 서버(Server Action/BFF) → BE 순으로 가고, 토큰 주입은 Next 서버가 한다.

> ⚠️ **비밀번호 변경·재설정 화면이 없다.** 재발급은 Admin에게 요청하는 구조다. 첫 비밀번호를 메일로 보내므로 **최초 로그인 시 변경 강제 여부**는 아직 미정 — BE 의견 필요.

## 4. 온보딩 (`/onboarding/1~3` → `/onboarding/payment` → `/onboarding/done`)

**대표(OWNER)가 최초 1회** 한다. 세 단계를 오가며 입력하고 **[다음]에서 한 번에 커밋**한 뒤,
**4단계에서 결제**를 마쳐야 워크스페이스가 열린다.

> ⚠️ **무료 요금제도 체험 기간도 없다**(2026-08-04). 결제를 건너뛸 길이 화면에 없다 —
> BE도 `UNPAID` 상태에서는 워크스페이스 API를 막아 달라. 화면만 막는 건 보안이 아니다.

> ⚠️ 지금 1~3단계 값은 브라우저 `sessionStorage`에 있다(탭 닫으면 사라진다). **커밋 엔드포인트가 생기면 이 임시 보관은 지운다.**

### 온보딩 진입 시 필요한 조회

```
GET /companies/me/departments     → 부서 트리
GET /companies/me/positions       → 직급 목록
```

둘 다 최초에는 **빈 배열**이면 된다(프론트가 데모 값으로 시작하지 않는다).

### 1단계 · 부서 체계

**2계층 고정 트리**다.

```
개발팀            ← 윗단 = 부서
 ├ 프론트엔드     ← 아랫단 = 그 부서 안의 "역할"
 └ 백엔드
경영지원          ← 아랫단은 비어 있어도 된다
```

| 규칙           | 값                                                                    |
| -------------- | --------------------------------------------------------------------- |
| 최대 깊이      | **2** (부서 > 역할). 3계층은 프론트가 아예 못 만들고, 들어오면 버린다 |
| 이름 최대 길이 | **5자** (3단계 셀렉트 칸 폭에서 역산한 값)                            |
| 아랫단         | **비워도 된다** — 부서에 바로 소속되는 사람이 있다(팀장이 그 경우)    |
| 사원의 소속    | **부서에** 소속된다. 권한은 부서가 아니라 **직급**에서 온다           |

BE 스키마도 **깊이 2를 강제**해 주면 좋다. 무제한 트리로 열어두면 프론트가 못 그리는 데이터가 들어온다.

### 2단계 · 직급 체계

**직급명과 권한(role)은 분리**된다. 이름은 회사마다 다르게 쓰고, 권한은 이름과 무관하게 직접 고른다.

```
{ id, name: "책임", role: "LEADER" }
{ id, name: "사원", role: "MEMBER" }
```

- `role`로 고를 수 있는 값: **`OWNER` · `LEADER` · `MEMBER`** (`SYSTEM`은 서비스 운영자라 제외)
- **`ADMIN`은 여기에 없다.** 직급이 아니라 **사람에게** 붙는 겸직 권한이라 3단계에서 켠다.
- 대표(`OWNER`) 계정은 승인 때 이미 만들어져 있다 — 직급 매핑 대상이 아니고, 화면에는 고정 표시만 한다.

### 3단계 · 사원 초대 = **계정 발급**

**한 줄이 곧 계정 하나**다.

```
{ email, departmentId, roleId, positionId, isAdmin }
```

| 필드           | 의미                                                                |
| -------------- | ------------------------------------------------------------------- |
| `email`        | 계정 ID이자 안내 메일 수신지                                        |
| `departmentId` | 소속 부서(트리 윗단)                                                |
| `roleId`       | 부서 안의 역할(트리 아랫단). **빈 문자열이면 "없음"** — 부서에 직속 |
| `positionId`   | 2단계에서 만든 직급                                                 |
| `isAdmin`      | **Admin 겸직.** 역할을 대체하지 않고 그 위에 얹힌다                 |

프론트가 이미 거는 규칙 — **BE도 같이 걸어야 한다:**

- 이메일 형식 검사 + **중복 주소는 첫 줄만 발송**(같은 사람이 두 번 받지 않게)
- **부서마다 LEADER는 한 명** — 두 번째 줄은 오류로 표시된다
- `isAdmin`은 **`LEADER`·`MEMBER`만** 가능. `OWNER`는 겸할 수 없다 (BE 응답에 OWNER+isAdmin이 와도 프론트는 무시한다)
- Admin 인원 제한은 **없다**

### [완료] — 한 번에 커밋

프론트가 필요로 하는 것은 **하나의 커밋 엔드포인트**다. 단계별로 나누면 중간에 이탈했을 때 반쪽짜리 조직이 남는다.

```
POST /companies/me/onboarding
  req  : {
           departments: [{ name, children: [{ name }] }],
           positions:   [{ name, role }],
           invites:     [{ email, departmentPath|departmentId, roleName|roleId,
                           positionName|positionId, isAdmin }]
         }
  res  : 200 { departmentCount, roleCount, positionCount, invitedCount }
                                          // 완료 화면 숫자를 이 응답으로 바꾼다
```

> ⚠️ **id 문제:** 부서·직급이 아직 서버에 없으므로 3단계의 `departmentId`·`positionId`는 **프론트가 만든 임시 id**다. 두 방법 중 하나로 정해 달라 —
> **(A)** 한 번에 보내고 BE가 임시 id로 연결(위 shape), **(B)** 부서·직급을 먼저 저장해 실제 id를 받은 뒤 초대를 보낸다.
> **(A)를 권한다** — (B)는 중간에 실패하면 부서만 만들어진 상태로 남는다.

> ⚠️ **초대 발송은 트랜잭션 안에 넣지 말아 달라.** 메일 발송 실패로 조직 생성까지 롤백되면 대표가 처음부터 다시 짜야 한다. 조직 저장 → 계정 생성 → 메일 발송 순으로, 메일 실패는 재발송 대상으로 남기는 쪽이 낫다.

## 5. 구독과의 연결 ⭐

- **초대 = 계정 생성.** "초대했지만 아직 안 들어온 사람" 같은 중간 상태가 없다.
- ⚠️ **인원은 과금 단위가 아니다**(2026-08-04). 몇 명을 초대해도 기본료는 그대로고,
  초대 때문에 금액이 오르지 않는다. **인원으로 막지 않는다.**
- 금액을 움직이는 건 **AI 토큰과 저장 공간** 두 축이다. 포함량을 넘긴 만큼만
  **다음 결제일에 기본료와 함께** 청구한다.
- **순서 한 줄기**(2026-08-05 확정) — 문서 안에서 이 순서 말고 다른 설명을 두지 않는다.

  ```
  3단계 [완료] → 조직·계정 저장(구독 UNPAID, 초대 메일 아직 안 감)
  4단계 결제 성공 → 구독 ACTIVE → **그때 초대 메일 발송**
  결제 실패      → 계정은 그대로, 구독 UNPAID 유지 → 다시 시도
  ```

  ⚠️ 계정을 먼저 만드는 이유는 **부서·직급을 붙여 둬야 결제 뒤 바로 열리기 때문**이다.
  대신 **메일은 결제 뒤에** 나간다 — 결제가 실패했는데 초대장이 먼저 가면 못 들어오는
  계정으로 안내한 셈이 된다(§정직성).

- ⚠️ **무료 요금제도 체험도 없다.** 결제를 마쳐야 워크스페이스가 열린다.

## 6. BE 답이 필요한 것 (미정)

1. **기업 승인을 사람이 하나, 자동인가?** — 화면 문구가 "검토 후 승인" 기준으로 쓰여 있다.
2. **비밀번호 정책**(길이·문자 종류) — 알려주면 화면 검증에 반영한다. 지금은 빈 값만 본다.
3. **최초 로그인 시 비밀번호 변경을 강제하나?** — 첫 비밀번호를 메일로 보내므로.
4. **온보딩 커밋을 (A) 한 방에 / (B) 단계별로** 중 무엇으로 할지. 프론트는 (A) 기준으로 짜여 있다.
5. **`isOnboarded`를 세션에서 주나?** — 없으면 로그인 후 어디로 보낼지 매번 조회해야 한다.
6. **`isAdmin`·`departmentPath`를 토큰/세션에 담을 수 있나?** — 없으면 권한 판정이 성립하지 않는다.
7. **기업 코드 형식** — 프론트 목은 `NOVA-7K3D`(영문+하이픈+영숫자 4자)로 두고 있다.

# 부록 B. 상태·에러 코드 약속

| 상황                    | HTTP | body                                      | 프론트 동작               |
| ----------------------- | ---- | ----------------------------------------- | ------------------------- |
| 폼 값이 틀림            | 400  | `{ errors: { 필드명: "문구" } }`          | **필드 밑에 인라인** 표시 |
| 목록 줄이 틀림          | 400  | `{ errors: [{ index, field, message }] }` | 해당 **줄만** 빨갛게      |
| 자격증명 불일치         | 401  | `{ message }`                             | 폼 위 한 줄               |
| 권한 없음               | 403  | `{ message }`                             | 폼 위 한 줄 / 화면 잠금   |
| 구독 없음 · 만료        | 402  | `{ code: "SUBSCRIPTION_REQUIRED" }`       | **결제 화면으로 유도**    |
| 중복(사업자번호·이메일) | 409  | `{ message }`                             | 폼 위 한 줄               |
| 서버 오류               | 5xx  | 무엇이든                                  | `error.tsx` 전체 화면     |

> ⚠️ **폼·목록 오류는 화면에 띄울 문장으로** 주면 좋다(~합니다체). 프론트가 문구 표를 따로
> 들고 있으면 그 표는 반드시 BE와 어긋난다.
>
> ⚠️ 단 **결제 실패만은 코드로** 준다. 카드사 사유는 종류가 많고 그대로 띄우면 사용자가
> 무엇을 해야 할지 모른다 — 아는 코드만 우리 문구로 옮기고 나머지는 일반 문구로 내린다.

# 부록 C. 화면이 한 약속 = BE가 지켜야 하는 제약

> **여기 적힌 문장은 전부 화면에 실제로 떠 있는 말이다.** 사용자가 읽고 그대로 믿는다.
> BE가 이대로 동작하지 않으면 **화면이 거짓말을 한 게 된다** — 고쳐야 할 쪽은 보통 BE가 아니라
> 이 표다. 못 지킬 약속이면 **문구부터 지워 달라.**
>
> ⚠️ 전례: 온보딩 초대 문구에 "링크는 7일간 유효해요"가 있었는데, 실제 방식이 링크 가입이 아니라
> **계정 발급**으로 정해지면서 그 문장이 통째로 거짓이 됐다. 근거 없이 적은 기한·개수는
> 그대로 계약이 된다.
>
> **✅ 표시는 2026-08-04에 화면 문구를 고쳐 위험을 없앤 항목**이다. 나머지는 팀이 확정한 정책이라
> 문구가 아니라 **BE 구현으로** 지켜야 한다.

## C-1. 결제 · 사용량

| 화면 문구                                                                       | BE가 보장해야 하는 것                                               | 위험                                     |
| ------------------------------------------------------------------------------- | ------------------------------------------------------------------- | ---------------------------------------- |
| "초과분 ₩X이 **다음 결제일에 기본료와 함께** 청구돼요"                          | 초과분을 그 자리에서 받지 않고 **다음 청구서에 합산**               | 즉시 청구하면 "왜 지금 빠졌냐"가 된다    |
| "**지금 쓰시는 데는 아무 제한이 없습니다**"                                     | 포함량을 넘겨도 **막지 않는다**(하드캡 없음)                        | 막으면 회의 중에 AI가 멈춘다             |
